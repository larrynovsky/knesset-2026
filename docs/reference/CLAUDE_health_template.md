## C. Среда: где живёт код и кто пишет

**Studio** (`larry@studio`, Tailscale) — single canonical: production-код, git-репо, БД, launchd.
**MacBook** — единственный писатель: правки через file-tools → `git commit` → `post-commit` пушит на Studio (`git push`) + рестартит бота. `run_checks.sh` бежит на MacBook.
**Cowork** — смонтирована iCloud-папка `health` (БД-зеркало, доки). Движок на Studio читается через Desktop Commander + `ssh`. ⚠️ В SSH PATH нет Homebrew — Python полным путём `/opt/homebrew/bin/python3.11`. Запись кода — через Desktop Commander в MacBook working copy (`/Users/larry/health_scripts`) → commit; ssh к Studio — только чтение/запуск.

**Доступ к файлам (агент):**
- **Нет прямого доступа к файлу → обязателен файловый менеджер** (напр. Desktop Commander). Читать/править файл через него, а не сдаваться и не перекладывать на пользователя.
- **Файловый менеджер не отвечает → 10 попыток с интервалом 6с** прежде чем прерваться. Разрыв моста часто транзиентный; не прекращать после первого отказа.
*Enforcement:* **MANUAL** (дисциплина агента).

**Деплой-путь:** `git push` (Studio `receive.denyCurrentBranch=updateInstead`), не rsync. Защиты: fast-forward only; отказ при dirty working tree на Studio.

**CHANGELOG и версию BLUEPRINT заполняет `doc_agent` на post-commit — руками не писать.** Строка генерируется из subject коммита и вставляется ПОСЛЕ него, поэтому написанная вручную не заменяется, а дублируется другой формулировкой того же коммита (наблюдалось дважды за сессию 2026-07-27). Машинного принуждения тут нет и не будет: две строки за один день по одной подсистеме — законный случай, а отличить его от дубля можно только по смыслу. Дисциплина: пишешь commit message — этого достаточно; хук допишет и оставит артефакт в индексе, забирай его следующим коммитом (§1).

**После ssh-запуска кода на Studio** (тесты, генерация, миграции — это разрешено, это не git-commit): следующая сессия MacBook начинается с `git fetch studio && git reset --hard studio/main`, иначе push упадёт fast-forward.

## D. Нормативные правила

Формат: **§-ID · норма · Enforcement · Rationale-ссылка.**
Enforcement: **LIVE** (исполняемый хук/тест) · **PARTIAL** (частично) · **MANUAL** (дисциплина, без автомата).

### D.1 Git и согласованность canonical

**§1 — Незакоммиченное на canonical = латентная потеря.** Не оставлять правки в working tree «на потом»: теряются при любом `reset`/`checkout`/`merge`.
*Enforcement:* **LIVE** — `uncommitted_watchdog.py` (ежечасно, launchd `com.larry.health.uncommitted-watchdog.plist`), Telegram-алерт при dirty >60 мин.
*Rationale:* [`docs/explanation/git_architecture.md §«Урок 2026-05-10»`].

**§2 — Pre-destructive diff перед `reset`/`checkout`/`merge`.** Сверить критичные файлы до операции, меняющей working tree.
*Enforcement:* **MANUAL** — `scripts/pre_destructive_check.sh`. Под git-моделью предпочесть `git status`/`git stash`.

**§3 — Backup перед destructive-операцией.** `cp -a` снапшот, хранить ~30 дней.
*Enforcement:* **MANUAL** + `backup.sh` (daily 03:00) покрывает рутину.

**§6 — ⚰️ RETIRED.** Сессионный rsync-протокол удалён (2026-06-28). Доставка кода — `git push` (post-commit). Скрипты `sync_*_studio.sh` удалены.

**§10 — Unstaged = shared state в multi-session.** При паузе с blocked-by-precommit И подозрении на параллельную сессию — немедленно `git stash push -u`.
*Enforcement:* **MANUAL** (суждение по detection-сигналам).
*Rationale:* инцидент 2026-06-15 (захват unstaged-секций чужим commit).

**§12 — Зелёный на не-той версии = ложно-зелёный. Перед доверием к прогону/integrity на Studio сверь, что ПРОВЕРЯЕМЫЙ коммит присутствует на Studio** (`git log studio/main` содержит твой HEAD; строгое `HEAD==HEAD` слишком жёстко — параллельный свежий коммит даёт транзиентный лаг). Результат теста действителен только против артефакта, который он реально исполнил; деплой (`git push` post-commit, updateInstead) может **молча** упасть (dirty Studio tree, divergence), записав это лишь в `deploy.log` → «регресс на Studio» гоняется на недеплоенном коде. Локальный MacBook-прогон НЕ заменяет проверку деплоя.
*Enforcement:* **LIVE** — post-commit при `push FAILED` шлёт громкий Telegram (Studio-notify, троттл 15м); `uncommitted_watchdog` (hourly, cooldown 4ч) ловит стойкую грязь Studio с деплой-блок-сообщением. **MANUAL** — перед аргументом «прошло на Studio» проверить, что `git log studio/main` содержит проверяемый коммит.
*Rationale:* инцидент 2026-07-05 — деплой молча падал 25ч (Studio dirty от параллельной сессии BL-LAB-CANON-2, правившей Studio в обход §8 single-writer); работа C стояла на MacBook, «регрессы на Studio» часами ложно-зелёные (валидировали старый код). Ср. [[feedback_stale_nightly_verdict]] (time-staleness), §10 (unstaged shared state). [`docs/how-to/multi_session_protocol.md`].

### D.2 Целостность данных

**§8 — Canonical-only generation + единственная canonical `health.db` (R1/R2).** Любой генератор/хук/скрипт, пишущий в репо или БД, — только на Studio (hostname-guard). `health.db` обязан жить ТОЛЬКО на локальном диске Studio; в iCloud/синк-папках/корне репо — запрещён (split-brain).
*Enforcement:* **LIVE** — `integrity_tests.check_single_canonical_db()` (FAIL в ночном triage); `get_conn` raise на не-Studio; `_validate_db_path()` raise при импорте; hostname-guard в `gen_*.py`; `tests/consistency/test_single_canonical_db.py`.
*Rationale:* инцидент 2026-06-18 (iCloud-форк разошёлся с каноном). [`docs/explanation/git_architecture.md`].
*Примечание:* самый нагруженный ID — 9 ссылок в коде. Не переименовывать.

### D.3 Качество кода

**§7 — Запрещён `except: pass` без лога или `# silent-ok: <reason>`** (или узкий `except <Specific>`). Baseline LIVE-кода = 35; превышение = drift-нарушение.
*Enforcement:* **LIVE** — `pre_commit_check.py` (INV-DOC-9) блокирует commit при превышении baseline; конвенция `# silent-ok:` используется (напр. `integrity_tests.py`).
*Открытый класс:* AST-скан на `pass` поверхностен, не ловит `NameError` под маской. Глубже — smoke-тесты entry-point'ов агентов (backlog).
*Rationale:* инцидент 2026-05-11 (`morning_report.py` неделю глотал `NameError`).

**§5 — Contract-тесты для публичного API.** Публичная поверхность модуля = объявленный контракт (`check_contracts.py`); каждая публичная функция с required-параметрами — под проверкой существования/сигнатуры.
*Enforcement:* **LIVE** — `check_contracts.py` (health_db: 87 функций после рефакторинга 2026-06-27) + `tests/unit/test_health_db_signatures_contract.py`.
*Rationale:* регрессия BUG-AGENTREPORTS-SIG 2026-05-10. [`docs/explanation/test_architecture.md`].

**§9 — Код = логика и мёртвый скелет; всё осмысленное — данные.** В коде остаётся только структура суждения и неизменяемый скелет. Любое число или имя, несущее клинический/методологический смысл и способное сдвинуться, — это данные: у них есть оракул и версионируемый дом вне кода. Структура правила («сравни метрику с baseline, ниже порога — флажь») живёт в коде; пороги, множители, баллы, имена — нет.
*Дискриминатор (единственный тест):* число — данные, если меняется по любой оси — возраст · новое исследование · состояние пациента · развитие методологии. Не меняется ни по одной → константа. Презумпция — выноса; бремя доказательства на том, кто оставляет число в коде.
*Закрытый список констант (всё прочее клиническое/методологическое = нарушение):* (1) арифметические факты (`мин = час·60`); (2) системная механика (`_PRIMARY_HOST="Studio.local"`, пути, лимит WAL, ретраи, TZ); (3) структура/представление (`>= 0`, срезы `[11:16]`, `len(x) > 0`, guard устойчивости `abs(r) < 0.01`); (4) seed-дефолт с доказуемым контуром БД — на init пишет в таблицу + рантайм читает из таблицы (не из литерала) + переопределяемо по контексту (эталон `DATA_FRESHNESS`). Seed без записи-и-чтения через БД = замаскированный хардкод.
*Три дома данных — разные оракулы, не сваливать в один:* нормы тела (`sleep<70`, `bp>=140`, множители `hrv<avg·0.82`) → таблица порогов, оракул — ты (личное/контекстное) + литература (популяционное); методологический рубрикатор (IC-скоринг гипотез) → оракул ты-методолог; конфиг анализа/политик (минимумы выборки, доли мониторинга, время суток) → оракул ты-инженер. Имена врачей/лабораторий/панелей → `doc_patterns`.
*Enforcement:* **MANUAL** (честно). Аудит 2026-06-28: §9-линтера в pre-commit НЕТ (там только INV-DOC-1/9); прежнее «Слой 1 — pre-commit» было аспирационным (само нарушало §4). Поток F строит: commit-линтер (флажит ВСЕ осмысленные литералы вне закрытого списка; baseline-ратчет — легаси не блокирует, новое сверх baseline → блок) + аудит оставленного (реестр вердиктов число·вердикт·обоснование·дата·оракул; триггер событийный + ~квартальный потолок; спорное «вынести» → задача с эскалацией).
*Тест нарушения:* `if "<имя>" in name`, либо числовой порог в оценке здоровья/метода, не входящий в закрытый список из 4 пунктов.
*Rationale:* норма дрейфует по возрасту/науке/состоянию — захардкоженная молча устаревает, и система уверенно считает по неверному порогу. Данные в коде делают модуль непереписываемым. Сформулировано из разговора + первого прогона аудита (90 кандидатов, концентрация в `morning_report`/`lifestyle_agents`) 2026-06-28.

**§15 — Новый модуль обязан быть одноразовым либо объяснить, почему нет.** Единица безопасности — не маленький модуль, а модуль за тестируемым контрактом, который можно переписать с нуля, имея только контракт и его тесты. Размер вторичен, контракт первичен. **Чек-лист (D1–D6) и числа — НЕ здесь:** единственный дом — `project_context/disposability.json` (методология, домен-агностична) + переопределение чисел в `project_context.json`, читать через `indexer.disposability_policy()`. Пересказ пунктов в своде был бы вторым домом и разъехался бы молча. Новый `.py` приносит сайдкар `contracts/<модуль>.json`: публичная поверхность · соседние контракты, на которые опирается · вердикт (6 пунктов, знак, обоснование, дата, оракул). Отрицательный вердикт ЛЕГАЛЕН — нелегально его отсутствие; `not_disposable` обязан нести `cause` (стабильный ключ, иначе повтор нельзя посчитать).

*Enforcement:* **LIVE** — `project_context dispgate --block` в pre-commit (exit 6) на файлах со статусом `A`: K1 сайдкар/совпадение поверхности/полнота вердикта/`depends_on` разрешается в существующий контракт или несёт пометку `legacy` с причиной · K2 тест импортирует модуль и зовёт публичное имя СВЯЗАННЫМ AST-вызовом · K3 нет обращений к чужим `_private` (сиблинги внутри пакета — не чужие) · K4 размер = WARN, никогда блок. **Всё судимое читается из ОДНОГО снимка индекса** (`project_context/staged.py`): рабочее дерево гейт не открывает, поэтому частичный стейдж не проходит. Отказ движкового чек-листа (`disposability.json` не прочитан) = блок, а не warn: это отказ инструмента суждения. **Внутренняя ошибка гейта БЛОКИРУЕТ, а не пропускает** (2026-07-27): отказ окружения гейт выражает структурно, поэтому исключение означает дефект гейта либо нераспознанный вход, и тихий проход по нему делал бы тихим каждый будущий дефект в этом коде. Контроли двухслойные — `tests/unit/test_dispgate.py` (чистый evaluator, позит раздельно по каждому пункту) и `tests/integration/test_dispgate_hook.py` (настоящий путь CLI→check→снимок→git в одноразовом клоне; на коде до ремонта 8 из 12 красные). **Честно про силу контролей:** мутациями проверены K1–K4 и границы снимка; контроль границы «движок из пакета против содержимого из индекса» — грепом по исходнику, то есть проверяет написание, а не поведение. `integrity_tests.check_dispgate_liveness` на Studio — **liveness, а не покрытие каждого правила**: он подсовывает грубого нарушителя, которого останавливает уже K1, и потому не заметит смерть K2/K3/K4 по отдельности. **MANUAL** — сам вердикт.
*Граница (не потерять):* K1–K4 ловят отсутствие НОСИТЕЛЯ, не его качество. Зелёный гейт доказывает, что суждение вынесено и записано, а не что модуль одноразов. D1 и D6 не проверяются никак — они живут только в вердикте. Вердикт — test с tacit-оракулом и машинно не выводится ПРИНЦИПИАЛЬНО, а не «пока не написали линтер».
*Периметр:* НОВЫЕ файлы — машинно-проверяемый предикат. Исключение ровно одно и оно про отсутствие ПРЕДМЕТА, а не про имя файла: `__init__.py` без определений функций и классов. Прежний blanket-фильтр по ведущему `_` снят 2026-07-26 (DG-03) — подчёркивание есть соглашение об именовании, а не граница способности; формулировка «периметр тотален» была переоценкой, внутри него жила зона с другим путём кода. Легаси вне периметра осознанно (аудит модулей ведёт Саша отдельными сессиями), поэтому baseline-механизма нет и он не нужен.
*Известные дыры (названы, не закрыты — ОСОЗНАННОЕ решение владельца, а не долг):* битая дата в вердикте проходит K1 и обнуляет счётчик недель (DG-05) · `getattr(mod, "_private")` обходит K3 (DG-06) · переименование не считается новым файлом (DG-12) · отказ git даёт fail-open — общая политика семьи из трёх гейтов, решается не в одиночку (DG-13) · **застейдженный symlink** (режим `120000`) уводит судимые байты за границу индекса: имя в снимке, содержимое снаружи (2026-07-27 F-01) · **`legacy` требует непустую строку, но не осмысленность** — `"потом"` пройдёт, и это принято: осмысленность неотличима машинно · **K2 доказывает СИНТАКСИС, не исполнение** — вызов без единого ассерта законен, поэтому усиление детектора не закрывает главный сценарий (плохой тест), см. how-to. Воспроизводятся: `plans/verify_dispgate_findings_2026-07-26.py` (раунд 1) и `plans/verify_dispgate_r2_findings_2026-07-27.py` (раунд 2). Там же зафиксировано, какие дефекты закрыты и обязаны оставаться закрытыми.
*Почему список не сокращается до нуля:* цель гейта — повысить вероятность, что суждение вынесено и характеризация существует, а не доказать корректность произвольной Python-программы на pre-commit. Каждая оставленная дыра стоила бы больше кода, чем даёт защиты, при модели «один доверенный писатель и агенты».
*Повтор причины:* одна причина в 3 разные календарные недели → вопрос об архитектуре, оракул человек. Урок печатается в `preflight` тому, кто здесь работает; человеку — только остаток. Гасится пометкой в `disposability.resolved_causes`.
*Rationale:* формулировка 2026-06-26 жила прозой в объяснении — её не читал ни человек при проектировании, ни машина на коммите. [`docs/explanation/disposable_modules_refactor.md`], [`docs/how-to/disposability_gate.md`], план [`plans/PLAN_disposability_gate_2026-07-26.md`].

### D.4 Мета-принципы

**§4 — Риск → runnable check, а не пункт в плане.** Найденный pre-flight риск превратить в исполняемый скрипт/тест, не в строку плана («намерения подводят через 24 часа»).
*Enforcement:* **LIVE как принцип** — воплощён в `pre_destructive_check.sh`, `uncommitted_watchdog.py`, integrity-проверках.
*Rationale:* инцидент 2026-05-10 (записал «сравнить .py» в план, не выполнил).

**§11 — Новое правило прогнать по своему вводящему изменению + сверить со сводом.** Формулируя норму из инцидента, до «готово» сделать две проверки: (a) **догфудинг** — применить правило к диффу, который его ВВОДИТ (слепое пятно — освобождать текущее изменение: «этот случай другой», «временно», «на всякий случай»); (b) **сверка со сводом** — против существующих §-правил и design-принципов на противоречие/дубль. Правило бывает верным по тексту и одновременно нарушаемым собственной реализацией. Особый подозреваемый — escape-hatch/флаг/fallback, добавленный «чтобы вдруг не сломать»: проверить, не экземпляр ли он того, от чего правило защищает.
*Enforcement:* **MANUAL** (суждение при формулировании нормы).
*Rationale:* BL-LAB-CANON-1 2026-07-04 — правило «старый писатель реактивируется через env» ввёл фиксом, добавившим env-хатч `HEALTH_ALLOW_BIOCHEMICAL_LABWRITE` (сам реактиватор); поймала только сверка со сводом (design-принцип «жёсткое > гибкость»). Класс повторный — ср. D.3-инцидент `pre_commit_check` v1, нарушавший правило, проверку которого реализовывал. [`memory feedback_rule_self_application`].

**§13 — Эскалация к человеку последняя, не первая.** Лестница ответа на обнаруженную проблему; человек — только на верхней ступени: (1) **авто-ремонт** — детерминированное безопасное действие система делает сама, с логом; (2) **fail-closed** — если ремонт небезопасен, но верно остановить вредное — блокируй без вопроса (`get_conn` raise §8 — это оно); (3) **эскалация** — ТОЛЬКО когда безопасного авто-действия нет И блок не решает, ЛИБО человек единственный оракул (медицинское/методологическое/необратимый выбор при неполной инфо); при эскалации назвать ПОЧЕМУ только человек.
*Envelope авто-ремонта (все обязательны):* (a) safe-предикат тотальный и машинно-проверяемый; (b) ресурс не редактируется активно; (c) доказуемо не теряется уникальной информации (предпочесть `stash`/пометку — `delete`/`discard`); (d) логируется + оставляет след рецидива. Не выполнено хоть одно → ступень 2 или 3. Эскалируй СТОЙКОЕ, не транзиентное (транзиент сам заживает — ни ремонта, ни человека не надо).
*Enforcement:* **MANUAL** (при проектировании guard'а); при ревью каждого «→ Telegram alert» спросить «нельзя ли безопасно авто-починить?».
*Rationale:* инцидент 2026-07-05 — деплой-блок эскалировали (alert), человек игнорировал 25ч; грязь была проверяемым дублём → авто-`stash` решил бы без человека. Человек-оракул — дефицитнейший ресурс; эскалировать автоматизируемое = тренировать игнорировать алерты (banner-blindness). Валидирует человек-гейты (medrev_/SUPERSEDE — законный случай 3b). Догфуд: post-commit-alert (MS-2) сам нарушал §13 — дёргал на транзиентной гонке; дотюнен на стойкость. [[feedback_verify_deploy_before_trust]].

**§14 — Датчик безопасности обязан иметь сигнал живости; но liveness ≠ корректность.** Тихо умерший guard = ложная безопасность (полагаешься на защиту, которой нет). Каждый датчик, на котором завязана безопасность, — под liveness (heartbeat/last-run vs свежесть ожидаемого события). **Терминус (против ∞ регресса):** liveness сходятся к ОДНОМУ always-on корневому монитору (ночной integrity/triage), ему доверяем. **Оговорка:** heartbeat доказывает «запустился», не «работает корректно» — для критичных добавить smoke/behavior-проверку (ср. genome fake-green: крутился «жив», проверял мимо).
*Enforcement:* **LIVE** — `check_daemons_alive` (KeepAlive PID), `check_arbiter_liveness` (heartbeat vs активность), `check_watchdog_liveness` (uncommitted_watchdog last-run).
*Rationale:* инцидент 2026-07-05 — watchdog чинили, но у него не было liveness → умрёт молча, и защита от тихого деплой-отказа сама тихо откажет (who-watches-the-watcher). Ср. [[feedback_detection_without_delivery]], [[feedback_silent_failures_monitoring]].
